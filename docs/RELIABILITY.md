# Надёжность: отказоустойчивость, резервные копии, показатели

Отказоустойчивый контур описан в
[`back/docker-compose.ha.yml`](../back/docker-compose.ha.yml) и подключается
поверх основного compose-файла. Рабочий стенд работает на нём с 15.11.2026.
Сценарии отказов ниже выполняются на отдельном стенде `confhub-lab`, чтобы не
ронять рабочий:

```bash
cd back
sudo ./scripts/lab.sh up        # сборка, запуск, межсетевой экран
sudo ./scripts/lab.sh destroy   # удалить стенд вместе с томами
```

## PostgreSQL: Patroni + etcd

| Компонент | Количество | Назначение |
| --- | --- | --- |
| PostgreSQL 16 + Patroni | 2 (`postgres`, `postgres-2`) | лидер и синхронный standby |
| etcd | 3 | хранит, кто лидер; кворум 2 из 3 защищает от split-brain |

* Репликация синхронная: транзакция подтверждается клиенту после записи на оба
  узла. При отказе лидера подтверждённые данные не теряются.
* Лидер продлевает ключ в etcd каждые 5 с. Если ключ не продлён 20 с (`ttl`),
  standby становится лидером.
* Сервисы получают оба адреса: `postgres:5432,postgres-2:5432` с параметром
  `target_session_attrs=read-write`. Драйвер сам находит текущего лидера,
  отдельный балансировщик не нужен.
* Вернувшийся старый лидер догоняет кластер через `pg_rewind` и становится
  репликой.

Демонстрация:

```bash
sudo ./scripts/demo/postgres-failover.sh
```

Сценарий показывает состояние кластера, каждую секунду регистрирует
пользователя через API, убивает лидера `SIGKILL`, ждёт восстановления записи,
сверяет число подтверждённых записей с базой и возвращает старый узел.
Результат прогона 15.11.2026: запись восстановилась через 17.7–21.8 с (четыре прогона), подтверждено
7 записей, в базе 7.

## NATS JetStream: кластер из трёх узлов

* Три узла (`nats`, `nats-2`, `nats-3`), стрим `CONFHUB_EVENTS` хранится в трёх
  репликах (`NATS_STREAM_REPLICAS=3`). Запись подтверждается большинством.
* Кластер переживает потерю одного узла. Клиенты знают все три адреса и
  переподключаются сами.
* События публикуются из таблицы outbox: если брокер недоступен, событие
  остаётся в базе и уходит после восстановления.

Демонстрация:

```bash
sudo ./scripts/demo/nats-failover.sh
```

Сценарий находит лидера стрима, публикует события (регистрации), убивает лидера
`SIGKILL`, показывает нового лидера и продолжение публикации, возвращает узел.
Результат прогона 15.11.2026: новый лидер выбран через 4.6–7 с, счётчик сообщений
продолжил расти.

## Резервное копирование и восстановление

| Что | Чем | Когда |
| --- | --- | --- |
| Полная копия стенда: дамп БД, тома MinIO, NATS, Redis, образы, конфигурация | `scripts/backup.sh`, архив шифруется `age` | ежедневно в 03:00 МСК, `confhub-backup.timer` |
| Проверка архива и пробное восстановление БД во временную базу | `scripts/restore.sh --verify-db <архив>` | после изменения схемы и раз в месяц |
| Восстановление базы | `pg_restore --clean --create` | при потере данных |

Демонстрация на стенде:

```bash
sudo ./scripts/demo/backup-restore.sh
```

Сценарий считает строки, делает `pg_dump`, удаляет схему `identity_svc`
(регистрация отдаёт 500), останавливает сервисы, восстанавливает базу, запускает
сервисы и сверяет данные. Результат прогона 15.11.2026: данные совпали,
восстановление вместе с перезапуском сервисов заняло 6.8–8.3 с на базе стенда.

Служебные скрипты находят узел, принимающий запись, через
`scripts/pg-leader.sh`, поэтому работают при любом лидере. Полная копия и
пробное восстановление на отказоустойчивом контуре проверены 15.11.2026.

Копии лежат на том же сервере (`/srv/confhub-backups`). Потерю сервера они не
покрывают, пока архивы не копируются на внешнее хранилище.

## Параметры обслуживания

Цели выбраны по измерениям и так, чтобы стенд выполнял их в нынешнем виде.

### Что измерено

| Метрика | На какой вопрос отвечает | Измерение |
| --- | --- | --- |
| Доступность (SLO) | Какую долю времени API отвечает пользователю | 99.97 % за 14 суток (Prometheus, `avg_over_time(up[14d])`, худший из четырёх сервисов); 4 ответа 5xx на 81 200 запросов |
| RPO | Сколько последних данных теряется при отказе | 0 при отказе узла БД (4 прогона: подтверждено 7, в базе 7); полная копия раз в сутки |
| RTO | Через какое время сервис снова работает | узел БД 17.7–21.8 с; узел брокера 4.6–7 с; `restore.sh --verify-db` рабочего архива 1.2 ГБ — 61 с |
| MTTR | Сколько длится восстановление | узел: до 22 с автоматически; сервер: 8 ч 19 мин (26.10.2026, выключен в 02:02, включён вручную в 10:21) |
| MTBF | Как часто происходит отказ | сервер: 2 остановки за 126 суток (журнал загрузок с 12.07.2026), наработка 1340 ч на остановку; по узлам статистики нет |

### Целевые значения

| Параметр | Цель | Обоснование |
| --- | --- | --- |
| Доступность API за месяц | 98.5 % (до 10 ч 57 мин простоя) | Покрывает одну ночную остановку сервера без дежурного (8 ч 19 мин по факту) и плановые перезапуски; 99.5 % одна такая остановка нарушает |
| RPO при отказе узла БД | 0 | Синхронная репликация; при недоступной реплике Patroni временно переходит в асинхронный режим, поэтому гарантия относится к отказу одного узла |
| RPO при порче или удалении данных | 24 ч | Копия раз в сутки в 03:00 МСК; заявки подаются неделями, сутки можно восполнить |
| RTO при отказе узла БД | 30 с | Худший прогон 21.8 с: `ttl` 20 с плюс повышение реплики |
| RTO при отказе узла брокера | 10 с | Худший прогон 7 с; события на это время остаются в outbox |
| RTO восстановления БД из копии | 15 мин | 61 с расшифровка и `pg_restore`, около 40 с запуск сервисов; остальное — диагностика и решение оператора |
| MTTR остановки сервера | 8 ч | Дежурного нет: ночную остановку замечают утром |

### Достижимость цели по доступности

`A = MTBF / (MTBF + MTTR)`:

* отказ узла БД или брокера: `720 ч / (720 ч + 30 с)` = 99.999 % (MTBF — допущение: один отказ в месяц);
* остановка сервера: `1340 / (1340 + 8.3)` = 99.38 % (по журналу загрузок);
* плановые работы: 99.97 % (Prometheus за 14 суток, включая перевод стенда и развёртывания 15.11.2026).

Произведение — около 99.3 % в среднем; в месяц с остановкой сервера — около
98.8 %. Цель 98.5 % выполнима и не завышена.

Цель не покрывает:

* потерю сервера вместе с дисками — копии хранятся на нём же;
* длительную остановку: с 21.09 по 05.10.2026 сервер был выключен 14.7 суток,
  причина по журналу не установлена, в расчёт MTTR она не включена.

## Перевод стенда с одиночных узлов на отказоустойчивый контур

Данные одиночного PostgreSQL (том `pgdata`) и стрим одиночного NATS в кластеры
сами не переходят: их переносят через копию.

1. Остановить сервисы приложения.
2. Снять копии: `pg_dump -Fc` базы и `nats stream backup CONFHUB_EVENTS`.
3. Остановить старый проект (`docker compose -p confhub down`, без `-v`).
4. Запустить узлы данных нового контура: etcd, оба PostgreSQL, три NATS.
5. Восстановить базу на лидере
   (`pg_restore -d postgres --clean --if-exists --create`) и стрим
   (`nats stream restore`).
6. Запустить остальные контейнеры, применить `firewall.sh apply`, выполнить
   `firewall.sh test`.

Рабочий стенд переведён так 15.11.2026: простой 1 мин 45 с, число строк совпало
во всех 51 таблице (4042 строки), в стрим вернулись все 646 событий и 31
подписчик. Старый том `pgdata`, копии в `/srv/confhub-backups/pre-20261115-ha`
и образы `confhub-rollback:*` оставлены как путь отката.

## Что остаётся единой точкой отказа

* Сам сервер: все узлы кластеров работают на одной машине. Отказоустойчивость
  защищает от падения процесса или контейнера, но не от потери хоста.
* nginx, Redis, MinIO и Elasticsearch работают в одном экземпляре.
* Копии хранятся на том же сервере.
