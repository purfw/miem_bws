# Развёртывание ConfHub

Последний известный адрес стенда: `https://91.132.58.253/`. Приложение установлено в
`/srv/confhub`, а системный nginx завершает TLS и проксирует запросы в
Compose-шлюз на `127.0.0.1:18080`. Ниже описаны воспроизводимый ручной
деплой и CI-заготовка. На повторной проверке 05.10.2026 сервер доступен,
изменения установлены, HTTPS и основные пользовательские сценарии проверены.

## Состав

Один nginx на 443 отдаёт и приложение, и API с одного адреса, редирект с 80:

```
https://91.132.58.253/            → фронт (front/, Vite/React)
https://91.132.58.253/api/v1/…    → четыре Go-сервиса
```

Postgres, Redis-кеш, отдельный persistent Redis state, NATS JetStream, MinIO, Elasticsearch 8 и Mailpit
наружу не публикуются — доступны только внутри сети compose. Django admin
также не публикуется на внешнем nginx: доступ выполняется через SSH tunnel к
loopback-контуру.

Внутренние бизнес-API слушают TLS 1.3 на 8443, требуют клиентский сертификат
собственного CA и подпись HMAC. HTTP-порты не принимают `/internal/*`.
Состояние сессий, refresh tokens и nonce хранится в Redis state с AOF и
`noeviction`, отдельно от вытесняемого кеша каталога.

У сервера только IP, без домена. Начиная с 2026 года Let's Encrypt выдаёт
для публичных IP доверенные сертификаты профиля `shortlived` сроком на 6
дней. На рабочем стенде сертификат для `91.132.58.253` выпускает Certbot
5.7 в Docker, а `confhub-certbot-renew.timer` проверяет продление дважды в
сутки. Начальный самоподписанный сертификат в `back/secrets/certs`
сохраняется только как аварийный резерв.

Django-admin входит в production compose. Новая настройка использует Argon2id,
TOTP с запретом повторного кода, Redis lockout и короткую серверную сессию.
Старые PBKDF2-хеши поддерживаются при миграции до смены пароля.
Публичный `/admin/` обязан
возвращать 404; инструкция подключения и credentials хранятся только у
администратора сервера.

## Способ 1. Вручную на сервере

Собирает образы на самой машине, registry не нужен.

```bash
git clone <репозиторий> confhub && cd confhub/back
PUBLIC_HOST=91.132.58.253 ./scripts/deploy.sh
```

`deploy.sh` идемпотентен и на первом запуске сам создаёт:

* `secrets/jwt_ed25519.{key,pub}` — ключи для JWT;
* `secrets/certs/{fullchain,privkey}.pem` — временный самоподписанный TLS с IP в SAN;
* `.env.prod` — случайные пароли Postgres, служебных ролей, MinIO,
  `SERVICE_TOKEN_SECRET` и ключ закрытых ссылок;
* `secrets/admin-auth/credentials.enc` и отдельный `secrets/admin-auth/key` —
  зашифрованное хранилище административного хеша пароля и TOTP-секрета.

Первый запуск требует интерактивного терминала: пароль вводится скрыто,
новый `otpauth://` URI показывается один раз, после добавления в приложение
требуется ввести текущий шестизначный код. URI нельзя сохранять в тикеты,
логи терминала или отправлять внешним сайтам генерации кодов. Открытый
пароль и URI не записываются в файлы. Не запускайте setup из CI с записью
терминала.

Существующие `ADMIN_*` в `.env.prod` автоматически мигрируют в шифрованное
хранилище и удаляются из `.env.prod`. Старый `secrets/admin-credentials.txt`
удаляется только после успешной проверки нового хранилища. Миграция не
меняет пароль и TOTP-секрет: после неё нужна отдельная ротация, если старый
файл или резервные копии могли быть доступны другим людям.

Ключ и шифротекст монтируются в Django read-only, без старых `ADMIN_*`
в окружении контейнера. Это защита от случайного чтения текстового файла,
а не от root-доступа или копии, содержащей одновременно ключ и шифротекст.
Пароли PostgreSQL, SMTP и другие сервисные секреты пока остаются в `.env.prod`;
вынос в полноценный secret manager ещё не выполнен.

Затем собирает образы и поднимает стек через
`docker-compose.prod.yml` + `docker-compose.build.yml`.

Проверка рабочего стенда с доверенным сертификатом:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://91.132.58.253/healthz/conference
curl -sS https://91.132.58.253/api/v1/conferences | head -c 200
```

Порт 443 (и 80 для редиректа) должен быть открыт в фаерволе.

### Доступ в админку и смена 2FA

С компьютера администратора:

```bash
ssh -L 18081:127.0.0.1:18080 root@91.132.58.253
```

Не закрывая SSH, откройте `http://127.0.0.1:18081/admin/`.
Введите собственный логин, пароль и код из приложения-аутентификатора.
Публичный `https://91.132.58.253/admin/` намеренно недоступен.

Консоль разделена на страницы с общей навигацией. После входа `/admin/`
перенаправляет в первый доступный раздел; для текущих ролей это полномочия
организаторов. На desktop навигация находится слева, на экранах уже 768 px —
сверху в горизонтальной прокручиваемой полосе. Прямые ссылки и история
браузера работают независимо для каждого раздела.

| URL | Раздел | Просмотр | Действия |
| --- | --- | --- | --- |
| `/admin/verifications/` | Полномочия организаторов | Все четыре роли | `superadmin`, `moderator` |
| `/admin/applications/` | Заявки на доклады | Все четыре роли | `superadmin`, `moderator` |
| `/admin/accounts/` | Учетные записи по UUID | `superadmin` | Блокировка и разблокировка |
| `/admin/queues/` | Фоновые задачи | `superadmin`, `operator` | Повтор неудачного задания |
| `/admin/audit/` | Журнал действий | `superadmin`, `moderator`, `auditor` | Только просмотр |
| `/admin/users/` | Поиск пользователей и роли платформы | `superadmin` | Роли, блокировка и разблокировка |
| `/admin/team/` | Команда админки | `superadmin` | Приглашения, права и статус сотрудников |

Списки используют собственный `?page=`. Заявки на доклады дополнительно
фильтруются по `?status=submitted,under_review,revision_requested`; без
фильтра показаны все три состояния. После действия сохраняются страница и
фильтр, а сообщение описывает конкретный результат. Неподдерживаемые коды
сообщений не показываются. Возврат выполняется только в заранее заданный
раздел, без произвольного `next`.

Каждая страница загружает только свои данные. Ошибка одного источника
отображается в текущем разделе. Журнал читается постранично по 50 записей
через существующую роль `django_reader`; прямых записей в БД консоль не
делает. Недоступные разделы скрыты в навигации, прямой запрос к ним получает
оформленную страницу 403. Все изменения выполняются POST-запросами с CSRF.

На сервере, после обновления исходников, миграция без смены данных:

```bash
cd /srv/confhub/back
bash scripts/admin-auth.sh migrate .env.prod
HOST_PROXY_PORT=18080 docker compose -p confhub --env-file .env.prod \
  -f docker-compose.prod.yml -f docker-compose.build.yml \
  -f docker-compose.host.yml up -d --build --force-recreate django-admin
```

Для смены пароля, отзыва старого TOTP-секрета и старых сессий выполните
`bash scripts/admin-auth.sh setup .env.prod` в интерактивном SSH-терминале,
затем ту же команду пересоздания Django. Перед изменением обеспечьте
резервный SSH-доступ. Старые архивы не очищаются миграцией и требуют
отдельной проверки и согласованной обработки по политике хранения.

Отдельные администраторы добавляются интерактивно, каждый со своим TOTP:

```bash
bash scripts/admin-auth.sh add .env.prod --username moderator --roles moderator
bash scripts/admin-auth.sh list .env.prod
bash scripts/admin-auth.sh role .env.prod --username moderator --roles auditor
bash scripts/admin-auth.sh disable .env.prod --username moderator
```

Роли консоли: `superadmin`, `moderator`, `operator`, `auditor`. Последнего
активного superadmin отключить или лишить этой роли нельзя. Изменения
хранилища подхватываются без рестарта; старые сессии изменённой учётной
записи отзываются. Входы и отказы записываются в аудит без пароля и TOTP.

В интерфейсе админки раздел «Пользователи» позволяет искать аккаунты по email
или имени, назначать роли на платформе и блокировать доступ. Раздел «Команда
админки» доступен только superadmin: в нём создаются приглашения сотрудников,
изменяются их роли и отключается доступ. Модератор может проверять заявки и
организаторов, но не управлять правами пользователей или других сотрудников.

Приглашение действует 20 минут и используется один раз. Отправка почты для
него не нужна: администратор передаёт ссылку сотруднику, который открывает её
через собственный SSH-туннель, задаёт пароль и подтверждает собственную 2FA.
Роль пользователя на платформе сама по себе не даёт доступа к админке.

Для управления командой контейнер Django получает запись в зашифрованное
хранилище `secrets/admin-auth`. Каталог имеет владельца root и группу 0,
режим `2770`, файл `.lock` — `0660`, ключ и зашифрованные данные — `0640`.
Скрипты настройки поддерживают эти разрешения. При обновлении старой установки
перед пересозданием контейнера примените на сервере:

```bash
chgrp 0 secrets/admin-auth secrets/admin-auth/.lock
chmod 2770 secrets/admin-auth
chmod 660 secrets/admin-auth/.lock
```

Если 80/443 уже заняты системным nginx (например, на сервере с
ISPmanager), приложение следует публиковать только на loopback и завершать
TLS на системном nginx:

```bash
PUBLIC_HOST=91.132.58.253 HOST_PROXY_PORT=18080 ./scripts/deploy.sh
cp nginx/confhub.host.conf.example /etc/nginx/sites-enabled/confhub.conf
nginx -t && systemctl reload nginx
```

В этом режиме Compose не захватывает внешние порты и не затрагивает другие
виртуальные хосты. `confhub.host.conf.example` используется до первичного
выпуска сертификата, а затем заменяется на
`confhub.host.letsencrypt.conf.example`. Systemd unit и timer продления
лежат в `back/systemd/`.

### Наполнение

Публичная выдача пуста, пока не создана конференция. Внутренний контур
наружу закрыт, поэтому запрос идёт с самой машины и подписывается
`X-Service-Token`:

```bash
cd /srv/confhub/back
python3 scripts/internal-call.py POST "https://conference-svc:8443/internal/conferences" < conf.json
```

Порт 8443 наружу не проброшен — команда выполняется на сервере. Скрипт читает
HMAC из `.env.prod` и сертификаты operations из `secrets/mtls`; секрет не
передаётся в аргументах процесса. Поля
`conf.json` совпадают с `createReq` в
`services/conference-svc/internal/handler/internal.go`; минимум — `title`,
`slug`, `start_date`, `end_date`, `created_by`. Созданная конференция
появляется в `draft`; чтобы стала видимой:

```bash
echo '{"status":"registration_open"}' | \
  python3 scripts/internal-call.py PATCH "https://conference-svc:8443/internal/conferences/<id>"
```

### Внешние credentials

По умолчанию сервис сохраняет очередь писем, но доставляет их только в
Mailpit. Для реальной доставки в `.env.prod` задаются `SMTP_HOST`,
`SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TLS_MODE`, после чего
пересоздаётся `engagement-svc`. Для порта 587 обычно используется `starttls`,
для 465 — `implicit`; `none` допустим только для внутреннего SMTP без
аутентификации. Разрешённый адрес отправителя и режим TLS определяет провайдер.
Адрес, указанный при выпуске Let's Encrypt, не является SMTP credential.
Секреты вводятся непосредственно в `.env.prod` на сервере, не в репозиторий.
Без внешнего SMTP пользователи не получат ссылки подтверждения и сброса пароля.

Для Яндекс Почты используется `smtp.yandex.ru:465` с
`SMTP_TLS_MODE=implicit`. В `SMTP_USER` указывается адрес ящика, в
`SMTP_FROM` — тот же адрес. В `SMTP_PASSWORD` нужен отдельный пароль
приложения типа «Почта», а не основной пароль Яндекс ID. Создание пароля и
разрешение доступа почтовым программам описаны в
[инструкции Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others).
Храните `.env.prod` с правами `0600`. После изменения настроек пересоздайте
только `engagement-svc` с теми же Compose-файлами и проектом, которые
используются при обычном обновлении.

ORCID активируется только при наличии `ORCID_CLIENT_ID` и
`ORCID_CLIENT_SECRET`. В кабинете ORCID Public API Client должен быть
зарегистрирован точный redirect URI:
`https://91.132.58.253/api/v1/auth/orcid/callback`. Пока credentials пусты,
кнопка ORCID скрыта, а обычная аутентификация работает независимо.

### Регламентные задания и резервное копирование

На сервере `confhub-backup.timer` ежедневно в 03:00 по Москве запускает
`back/scripts/backup.sh`. Явная временная зона в systemd timer не зависит
от системной временной зоны хоста. Скрипт сохраняет дамп PostgreSQL, данные MinIO и
NATS, compose/nginx-конфигурацию, системный nginx, Let's Encrypt и секреты
в `/srv/confhub-backups`; права
каталога — `0700`, архивов — `0600`, срок хранения по умолчанию — 14 дней.
Это локальная страховка от логических ошибок. Elasticsearch в архив не
входит: индекс полностью восстанавливается из PostgreSQL и обслуживает
запросы по уже восстановленной части.

Новые резервные копии шифруются age. Закрытый ключ находится отдельно в
`/srv/confhub-backup-keys/identity.key` и не включается в архив. Его необходимо
сохранить вне сервера; потеря ключа делает архивы недоступными. Для согласованного
снимка скрипт кратко останавливает записывающие сервисы и сохраняет PostgreSQL,
MinIO, NATS, Redis state, конфигурацию и используемые Docker-образы. После снимка
сервисы запускаются до упаковки образов и шифрования. Старые незашифрованные
архивы не переписываются. `monitoring/backup/restore.sh`
делегирует проверку единому `back/scripts/restore.sh`:

```bash
bash scripts/restore.sh --check /srv/confhub-backups/confhub-<timestamp>.tar.gz.age
bash scripts/restore.sh --verify-db /srv/confhub-backups/confhub-<timestamp>.tar.gz.age
bash scripts/restore.sh --verify-stack /srv/confhub-backups/confhub-<timestamp>.tar.gz.age
```

Второй режим восстанавливает PostgreSQL в отдельную временную базу и удаляет
только её. Третий режим восстанавливает отдельный Compose-проект с собственными
томами PostgreSQL/MinIO/NATS/Redis, без внешних портов и выхода в интернет.
Проверяет готовность сервисов и публичные/внутренние API, затем удаляет только
этот временный проект. Production БД и тома не заменяются. Это проверка
восстановимости, не команда аварийного переключения пользователей.
Новые бэкапы исключают старый `admin-credentials.txt`, но прежние архивы не меняются.

Дополнительно устанавливаются timers:

* `confhub-certbot-renew.timer` — проверка IP-сертификата дважды в сутки;
* `confhub-audit-maintenance.timer` — подготовка monthly partitions и перенос
  записей старше 12 месяцев в MinIO-архив с удалением payload и идентификаторов
  в новых архивах; прежняя история автоматически не переписывается;
* `confhub-weekly-review.timer` — отчёт по аномальной активности,
  недоставленным сообщениям, outbox, диску и длинным SQL-запросам;
* `confhub-key-rotation.timer` — квартальная замена JWT и активного ключа
  закрытых ссылок с сохранением keyring и автоматическим rollback.
* `confhub-service-keys.timer` — ежемесячная замена межсервисного HMAC и
  проверка срока mTLS-сертификатов; сертификаты обновляются заранее.

Для DR при потере всего сервера локальные архивы нужно дополнительно
выгружать в независимое зашифрованное хранилище.

### API-документация и трассировка

Список маршрутов формируется из работающего роутера:
`/api/v1/openapi/identity.json`, `conference.json`, `application.json`,
`engagement.json` с тем же префиксом. Swagger UI находится по `/docs`.
Схемы DTO, multipart и ответов формируются из исходников; описаны статусы,
параметры, bearer/refresh-cookie и внутренний HMAC/mTLS. Все текущие маршруты
зарегистрированы; старт сервиса и тесты проверяют отсутствие пропусков.
Внутренние методы в документации не становятся публичными API.

Дата начала создаваемого или редактируемого мероприятия должна быть
не раньше 01.01.2027. Проверяется итоговая дата и при частичном PATCH;
старые записи автоматически не переносятся. Участие слушателем использует
`POST /api/v1/conferences/{id}/register` с `role_at_conf=attendee`, состояние
доступно через `GET /api/v1/conferences/{id}/registration`. Подача доклада
остаётся отдельной заявкой. Для участия требуется подтверждённый email.

Jaeger доступен только через loopback-порт 16686. Для просмотра:

```bash
ssh -L 16686:127.0.0.1:16686 root@91.132.58.253
```

Откройте `http://127.0.0.1:16686/`. HTTP и основные NATS-обработчики передают
W3C trace context. В атрибутах нет тел запросов, query string и токенов;
используются шаблоны маршрутов. Хранение трасс ограничено 48 часами,
выборка корневых запросов — 10%.

Не запускайте pytest через `docker exec` рабочего Django-контейнера:
среди проверок есть очистка тестового кеша. Используйте отдельный контейнер
без `.env.prod`, credentials и URL рабочих сервисов, с отдельным Redis
и `TEST_REDIS_URL=redis://confhub-test-redis-<уникальное-имя>:6379/0`.
Тестовый bootstrap отвергает рабочие настройки и адреса вне тестового
пространства имён.

### Обновление

```bash
git pull && PUBLIC_HOST=91.132.58.253 ./scripts/deploy.sh
```

Миграции применяются сервисами при старте. При loopback-overlay все compose
команды должны использовать проект `confhub`, `.env.prod` и файлы
`docker-compose.prod.yml`, `docker-compose.build.yml`,
`docker-compose.host.yml`; безопаснее повторно запускать `deploy.sh`, чем
вручную вызывать сокращённый `docker compose up`. Compose-шлюз использует
динамическое разрешение имён через Docker DNS, поэтому пересоздание frontend
или API-контейнера не оставляет nginx привязанным к его старому IP.
Если файл nginx был заменён через rsync, пересоздайте Compose-шлюз:
одного reload недостаточно для bind mount, оставшегося на прежнем inode.

## Способ 2. Через CI

В `.sourcecraft/ci.yaml` сейчас есть только сборка, линт, тесты и сканы —
джоб публикации образов и деплоя нет. Заготовка — в
`.sourcecraft/deploy.example.yaml`; чтобы её включить, devops'у нужно:

1. Реестр образов и переменная `CI_REGISTRY_IMAGE`, куда пушить.
2. Секрет с приватным SSH-ключом на сервер и его адрес.
3. Перенести содержимое заготовки в `ci.yaml` и проверить синтаксис
   cubes на раннере.

До этого деплой идёт способом 1.

## Фронтенд

React-приложение подключено к публичному API и полностью переключается RU/EN.
Оно устанавливается как PWA: manifest и иконки 192/512 доступны публично,
service worker кеширует только оболочку и статические ресурсы, не API и не
персональные данные.
Реализованы каталог Elasticsearch с поиском, фильтрами, сортировкой и
пагинацией; карточка и календарь; регистрация/waitlist/отмена; избранное и
подписки; заявки; документы; профиль; восстановление пароля; кабинет
организатора с CRUD события и программы; защищённое подключение к сессии.

Демонстрационный каталог наполняется идемпотентным скриптом
`back/scripts/seed-demo.py`: существующие конференции он не дублирует, а
черновики публикует через разрешённую цепочку состояний.
